= 5. Building Block View

The hub is a single Spring Boot backend built from feature packages, with a bundled React SPA as its browser client.
The Level 1 diagram shows the outward-facing blocks; the table below lists every block, including internal ones like `capability`, `room`, `floor`, and `web`.
Level 2 zooms into the three with real internal structure: `device`, `integration`, and `telemetry`.

== Level 1

automation --> db : JPA
settings --> db : JPA
@enduml
----

[cols="1,3",options="header"]
|===
| Block | Responsibility
| `frontend` | The dashboard: a React SPA (toolchain under `hub/frontend/`) that registers, lists, and controls devices, charts sensor history, groups them on a room floor plan, and hosts the AI chat. It sees only the REST contract, never the domain model.
| `web` | Cross-cutting web concerns: maps exceptions to RFC 9457 `ProblemDetail`, serves the SPA, and exposes the OpenAPI document.
| `device` | Application core: the device model plus register / list / control logic and persistence. It records inbound sensor readings and emits a reading event for the streaming side. Its parts are its <<wb-device,whitebox>>.
| `capability` | The neutral state and command vocabulary (on/off, brightness as %, color as CIE xy, color temperature in Kelvin) that every adapter speaks, so the core never learns a vendor's model.
| `room` | Groups devices into rooms (a Home Assistant "area"): a device belongs to zero or one room. Room CRUD lives here; the device core owns the assignment, so a room change rides the same live-update path.
| `floor` | Groups rooms into building floors (a Home Assistant "floor"): a room belongs to zero or one floor. Floor CRUD lives here; the room side owns the assignment.
| `integration` | The `DeviceAdapter` port and the registry that routes to it; one sub-package per ecosystem plugs in here. Its parts are its <<wb-integration,whitebox>>.
| `settings` | Persisted, auto-restored integration connections and keys, so a paired bridge, broker, inverter, or assistant key survives a restart.
| `telemetry` | The sensor-history read side (served over the API from a search index) and the publisher that puts each recorded reading onto the streaming topic. Its parts are its <<wb-telemetry,whitebox>>.
| `realtime` | Pushes device changes to the dashboard over Server-Sent Events (ADR 11), listening for the same device events the rest of the system already publishes.
| `automation` | A rules engine that acts on the hub's behalf: when a trigger fires and its conditions hold, it runs device actions through the same neutral command path the UI uses (ADR 12). It reacts to the same device and reading events the rest of the system already publishes.
| `assistant` | The AI control surface: it turns natural-language prompts into tool-use calls against the same device and telemetry services the UI uses.
|===

=== The `device` core

[plantuml,bb-device,svg]
----

ctl --> svc : register / list / command
svc --> model : mutate state
svc --> repo : load / save
repo --> db : JPA

svc --> port : route command
svc --> [telemetry] : reading recorded
svc ..> [realtime] : device changed / removed
@enduml
----

[cols="1,3",options="header"]
|===
| Part | Responsibility
| `DeviceController` | The REST surface: register, list, toggle, and command devices, and read their sensors.
| `DeviceService` | The core logic: resolves capabilities, routes commands through the adapter port, records readings, and emits change and reading events.
| `DeviceRepository` | Spring Data JPA persistence of the device aggregate.
| `Device` (model) | The device aggregate: its type, capabilities, state, and sensors.
|===

=== The `integration` package

[plantuml,bb-integration,svg]
----

skinparam componentStyle rectangle

[device core] as device
package "integration" {
  interface "DeviceAdapter\n(port)" as port
  [registry]
  [Hue adapter] as hue

device --> registry : route command
registry --> port
hue ..|> port
shelly ..|> port
hue --> plug
shelly --> plug
broker --> mqtt : subscribe
inverter --> solakon : poll (Modbus)
mqtt --> device : record readings
solakon --> device : record readings
@enduml
----

[cols="1,3",options="header"]
|===
| Part | Responsibility
| `DeviceAdapter` (port) | The neutral outbound port a command device is reached through.
| `DeviceAdapterRegistry` | Resolves the adapter for a device by its adapter type.
| Command adapters (`hue`, `shelly`) | Implement the port, translating a neutral command into the vendor's API.
| Telemetry listeners (`mqtt`, `solakon`) | Implement no command adapter; they feed readings straight into the core: MQTT by subscribing to a broker, Solakon by polling a solar inverter over Modbus.
|===

|===
| Part | Responsibility

| `TelemetryHistoryService` | Reads sensor history back from the search index.
| `TelemetryHistoryController` | Serves that history over the REST API.
|===
