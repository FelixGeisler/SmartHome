= ADR 8: Persist integration connections in a settings store

== Status
Accepted

== Context
Integrations are configured at runtime (ADR 5): a Hue bridge is paired, an MQTT broker pointed at, an assistant key entered. ADR 6 and ADR 7 deferred persisting these credentials, but re-establishing them on every restart is the wrong behavior for a hub. They are also a poor fit for the relational registry: a handful of singular settings, not rows in the device model.

== Decision
Integration connection settings are persisted in a dedicated key-value settings store, a `hub_setting` table separate from the device registry (ADR 7).

* On startup the hub reads each setting back and re-establishes the connection.
* Persisting a new kind of connection is a new key, not a schema change.
* Secrets are held at rest in the same local database, never logged, never returned by the API.

Persisted settings include the Hue bridge host and key, the MQTT broker, the Solakon and Homematic connections, the assistant API key, and the administrator credentials (ADR 13).

== Consequences
[cols="1,1",options="header"]
|===
| Gain | Cost
| A configured hub comes back as it was left: no re-pairing, no re-entering keys | Secrets sit at rest in the local store (accepted: the same trusted single-host machine as the hub)
| A new kind of connection is a new key, not a schema change | A networked or multi-tenant deployment would need encryption at rest and stricter handling
|===
