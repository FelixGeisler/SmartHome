= ADR 11: Push live dashboard updates with Server-Sent Events

== Status
Accepted

== Context
The dashboard must reflect changes it did not cause: a reading from a node, a device auto-provisioned from telemetry, or a light another client switched. It used to re-fetch the whole device list on a timer, adding latency up to the poll interval and refetching everything for every client on each tick. The hub emits domain events on every device change and reading, so the missing piece is pushing them to the browser.

== Decision
The hub pushes device changes to the dashboard over Server-Sent Events: a single endpoint streams named events, the browser subscribes once with the built-in `EventSource`, and commands continue over REST.

[cols="1,1",options="header"]
|===
| SSE (chosen) | WebSocket (rejected)
| Ordinary HTTP, same origin as the API, no new dependency or handshake | A separately negotiated, bidirectional protocol
| One-way server push, which is all this needs | Its only edge here is client-to-server messages over the socket, which this design never sends
|===

== Consequences
[cols="1,1",options="header"]
|===
| Gain | Cost
| Changes appear as they happen; an idle dashboard makes no repeated requests | Fire-and-forget: an event missed while briefly disconnected is not redelivered
| The stream carries only what changed, so the client applies small updates, not a full replace | The client re-syncs with a full fetch on reconnect
| Fan-out runs on its own thread, payload serialized once, so a slow client cannot hold up ingest or commands | The hub holds one open connection per client, bounded by a stream timeout after which the client reconnects
|===
