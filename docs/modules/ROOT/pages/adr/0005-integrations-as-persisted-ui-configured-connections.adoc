= ADR 5: Integrations as persisted, UI-configured connections

== Status
Accepted

== Context
The hub is a consumer product, set up entirely from the dashboard. A connection must survive restarts, be listed and removed in the UI, and show its status. Setup is not uniform: a simple form for one ecosystem, button-press pairing for a Hue bridge, an OAuth redirect for another. A single declared form covers only the first.

== Decision
An integration is configured from the dashboard and persisted, so it survives a restart. Because setup differs by ecosystem, each is its own controller and dashboard panel rather than a shared abstraction.

* Settings and secrets live in the settings store (ADR 8); on startup the hub reads them back and re-establishes the connection.
* A device is addressed by its bridge-local id; re-registering the same id is rejected, not duplicated.
* Secrets are never logged and never returned by the API.

== Consequences
[cols="1,1",options="header"]
|===
| Gain | Cost
| A configured hub comes back as it was left, with no re-pairing or re-entering keys | Adding an ecosystem is a new controller, adapter, and panel, not a config entry
| Each setup flow gets the UI it genuinely needs | No shared connection-management UI, reconfiguration, or reload without a restart
|===

Connection status reflects that setup completed, not live reachability, which the reachability monitor tracks separately.
