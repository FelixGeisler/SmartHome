= ADR 10: Stream telemetry through a broker into a search-index read model

== Status
Accepted

== Context
Sensor readings arrive continuously (ADR 6), but the registry keeps only the latest value per sensor (ADR 7). A relational registry is the wrong home for an ever-growing time series, and the hub should not store and query one itself. The dashboard still needs history to chart, and the readings should stay open to analytics tools without the hub growing an endpoint per question.

== Decision
Every recorded reading is published, keyed by device, onto a telemetry topic on a Kafka-API broker; the hub runs no consumer of its own.

[cols="1,2",options="header"]
|===
| Stage | What happens
| Publish | The hub puts each reading on the topic, fire-and-forget: a pipeline failure is logged and never fails ingest
| Sink | A standard connector sinks the topic into a search index
| Read | The hub's history endpoint queries that index
|===

The broker, connector, index, and its exploration UI run as a separate infrastructure stack beside the hub.

== Consequences
[cols="1,1",options="header"]
|===
| Gain | Cost
| Ingest and history are decoupled: a down pipeline loses history but not live state | History requires the infrastructure stack to run
| The topic is the single feed, so anything else taps it or the index without touching the hub, and moving data is connector configuration, not hub code | Fire-and-forget, so readings published while the broker is unreachable are not replayed (accepted: readings recur and the registry holds the latest)
|===
