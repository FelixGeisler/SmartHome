= ADR 12: Automate device actions with a rules engine on the domain event bus

== Status
Accepted

== Context
The hub should act on its own: when a sensor crosses a threshold or on a schedule, it runs device commands with no person in the loop. This is the Home Assistant and Matter shape of an automation: when a trigger fires, if conditions hold, then run actions in order. The hub already publishes a domain event on every reading and device change, and already routes neutral commands through a capability-checked service, so an engine mostly reacts to those events and drives that service. It must not become a bottleneck: telemetry ingest and command handling are hot paths, and a device an action targets may be slow or unreachable.

[cols="1,2",options="header"]
|===
| Rejected alternative | Why
| An opaque rule document | The engine has to query and index rules and join them to devices
| A separate message broker | The in-process event publisher already carries the events an automation reacts to
|===

== Decision
Automations are relationally persisted rules, evaluated by an engine that listens to the events the hub already emits and runs actions through the existing device service. New trigger, condition, and action kinds plug in behind small handler registries, the same ports-and-adapters seam the integrations use.

[plantuml,automation-flow,svg]
----
@startuml
left to right direction
skinparam componentStyle rectangle
[reading + device\nevents] as ev
[Automation engine] as eng
rectangle "Rule" {
  [Trigger\n(edge-triggered)] as t
  [Conditions] as c
  [Actions] as a
}
[Device service\n(neutral command path)] as svc
node "Devices" as dev

ev --> eng : react
eng --> t : on event / schedule
t --> c : fired
c --> a : all hold
a --> svc : run in order
svc --> dev : command
note bottom of eng : actions run on a bounded\nworker thread, off the publisher
@enduml
----

The engine edge-triggers, firing on the reading that crosses the boundary rather than every reading that stays past it, and runs actions on a dedicated worker thread so a slow device cannot hold up ingest.

== Consequences
[cols="1,1",options="header"]
|===
| Gain | Cost
| An action can do anything a user can from the UI, pushed live like any other change | Effects are eventually consistent with the triggering reading, not synchronous with it
| A new trigger, condition, or action kind is a handler plus a row type, not an engine rewrite | The edge-latch state lives in memory: it rebuilds after a restart and re-baselines on the next reading
| Rules reference devices by id without a foreign key, so a rule outlives a device it names | A stale device reference is handled at run time rather than prevented
|===
