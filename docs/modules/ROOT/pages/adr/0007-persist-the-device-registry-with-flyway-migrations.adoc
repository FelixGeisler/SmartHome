= ADR 7: Persist the device registry in an on-disk database with Flyway migrations

== Status
Accepted

== Context
The device registry lived only in an in-memory database, discarded on every restart, so every device had to be re-registered. That is especially wrong now that nodes auto-provision from telemetry (ADR 6): a node seen once should stay known. The schema was also generated from the JPA entities at startup, leaving no reviewable, versioned record of how it evolves.

== Decision
The device registry lives in an on-disk database so it survives restarts, with its schema owned by versioned migrations.

[cols="1,2",options="header"]
|===
| Choice | Rationale
| An embedded, on-disk file database | A single-process hub stays self-contained and survives restarts
| Flyway migrations are the source of truth | Entities are validated against the schema, not allowed to reshape it; changes are reviewable and versioned
| Enum columns stored as strings | The same migrations run unchanged against another database
|===

== Consequences
[cols="1,1",options="header"]
|===
| Gain | Cost
| A device registered or auto-provisioned once stays known across restarts | Evolving an entity means writing a migration and keeping the two in step
| Schema changes are explicit and history-tracked; a mismatch fails fast on startup | The file database is single-writer and local; a concurrent or distributed deployment would move to a networked database
|===
