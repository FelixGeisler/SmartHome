= ADR 6: MQTT as a runtime integration; sensor nodes auto-provisioned

== Status
Accepted

== Context
MQTT ingestion used to be gated by a startup flag, and every node and each of its sensors had to be registered up front. That is inconsistent with ADR 5, where integrations are configured at runtime, and it blocks simply plugging in a node. A node publishes a bare value per topic (`<prefix>/<node>/<sensor-key>`), with no measurement type or unit.

== Decision
The MQTT broker is a runtime-configured integration, connected and disconnected through the API like the others: connecting starts the telemetry subscription, disconnecting stops it. Inbound telemetry then provisions its own source.

[plantuml,mqtt-provisioning,svg]
----
@startuml
skinparam defaultTextAlignment center
start
:reading arrives\n<prefix>/<node>/<key>;
if (key in vocabulary?\ne.g. temperature,\nhumidity, CO2, power) then (no)
  :drop the reading;
  stop
endif
:provision the node\nif not yet known;
:add the sensor if new\n(measurement's default unit);
:record the reading;
stop
@enduml
----

== Consequences
[cols="1,1",options="header"]
|===
| Gain | Cost
| Connecting MQTT matches the other integrations; a node appears just by publishing | The hub understands only the fixed vocabulary, so a new measurement is a code change
| No manual registration to plug in a node | Auto-provisioned sensors carry inferred type and unit, not the richer declared metadata of ADR 2 and ADR 3
|===

The broker connection is persisted and re-established on restart like the other integrations (ADR 8).
