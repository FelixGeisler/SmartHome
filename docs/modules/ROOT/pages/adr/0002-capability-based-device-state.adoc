= ADR 2: Capability-based device state

== Status
Accepted

== Context
Devices vary: some switch, some dim or change color, some only report readings. Deriving behavior from a fixed device category can't tell two same-category devices with different abilities apart, and makes every new behavior a schema change.

== Decision
A device declares a set of capabilities, each a typed contract that owns the neutral attributes it reports and the commands it accepts.

* Capabilities *compose*; they are not inherited from a category.
* The set is fixed at registration or provisioning and stored on the device.
* A command using a capability the device lacks is rejected.
* Category drives grouping and icons only, never the command gate.
* Sensor readings are separate measurement channels, not capabilities.

== Consequences
[cols="1,1",options="header"]
|===
| Gain | Cost
| A new device kind is a list of capabilities; a new behavior is one capability plus its contract | State is stored as strings, so the contract, not the column type, enforces its shape
| The capability set is the single source of truth for the command gate, adapters, and dashboard controls | The set of capabilities is fixed in code, so adding one is a code change
|===
